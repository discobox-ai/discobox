# secrets review notes

- A rule answers, is proposed from, and is made from only a request that carries a policy: `ruleTestable`, `ruleProposable`, and the console's `CredentialRequest.Ruleable` say so together, and change together. A rule's policy is what a request's is held to, so a request with uses alone has nothing to hold.
- A rule's policy is compared with `policy.Within`, both sides resolved for the discobox that asked, and only `Unsettled` conditions reach the judge. Never put a whole policy, or a statement code found outside the rule, to the judge: a model asked "is this within" of a list leaks across items (ADR 26-10-20-782, Context). A rule never records resolved values; one that did would bind every later discobox to the first one's repository.
- The grant a rule mints carries the request's policy as asked, held to the values it resolved to when it was compared (`approvalWrite.shown`), never the rule's class.
- A policy handed on by a discobox goes through `delegationsCovering` before `judgeDelegations`, on every path that hands one on — an approval and a create. A path that judges only the uses hands on whatever policy came with them.
- Every field of a grant a rule mints is authorization somewhere downstream, so each must be one the rule held. A rule holds a request's policy, never its uses; a delegation's uses still bound a hand-off of uses alone, so a rule approves no delegation (`checkRule`, `ruleProposable`, `ProposeApprovalRuleFromGrant`, the console's `Ruleable` and its grant card) until that hand-off is gone (#312). Before lifting it, check nothing else reads a rule-minted grant's uses as authorization.
