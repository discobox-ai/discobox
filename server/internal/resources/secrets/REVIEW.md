# secrets review notes

- Nothing here judges (ADR 26-10-27-880). A check that needs to read what a request means, rather than where it goes, belongs in the pool's static routes, never in a model asked from here.
- A binding's route lists include its parent's: anything that changes a binding also marks the holders of its children.
- Every binding write — create, update, delete, cascade, expiry — records its event and marks the holders (`MarkBindingHoldersDirtyTx`) in the same transaction. A new path that writes a binding through the store without both leaves the history short or a discobox holding what it no longer may.
- A binding a discobox hands on — by approving a request or on a create — is a child of a live delegate binding covering it, of the same secret, no longer-lived than it, read again in the write's transaction (`lockHandoff`, `fitDelegation`). A new path that hands one on goes through both and sets `ParentID`.
- The project-level binding routes remain person-only; the target-addressed create permits bounded sentinel use by a current lead (ADR 26-11-04-389). Only a person makes a delegate binding, or answers — approves or denies — a request with a delegate part; a discobox never hands on the power to hand on.
- A resolve hands a value out only from a standing binding (`standingBinding`, read through `resolution`), and only by one of two doors: a swap for a host some live grant the sentinel is held to allows in every one of that grant's route lists, held by the pool until the latest of those grants lapses (`ResolveSandboxSecret`, `store.SentinelGrantsFor`, ADR 26-11-03-329 §3), which refuses a raw binding's handle; or a raw binding's value, with no host, only while its row and binding are raw and its secret allows raw, rechecked where the delivery is recorded (`ResolveSandboxRawSecret`, ADR 26-10-27-840). A new door shares `resolution` and `handOut` rather than repeating them. A sentinel with no binding resolves to nothing and opens no request.
- A raw binding is a person's: every binding write runs `checkRawBinding`, nothing a discobox writes or approves is raw, and no request asks for raw — the value is a person's choice when approving (`ApproveSecretRequestBody.raw`), never the ask's. An approval renews or removes a raw binding only when it grants the value again; a sentinel approval over one answers 409 (`checkReplaced`), because an approver reads a sentinel ask and renewing a handover through it widens what nobody looked at. A grant's delivery reaches the agent that asked: the request's status carries `raw` (handler, pool broker, `discobox-access`), since an agent told it holds a placeholder uses a file's path as a token. A raw binding on a harness config or the project reaches discoboxes a discobox created, by design (ADR 26-10-27-840 §2); do not "fix" that by filtering a level.
- A variable a discobox holds with another secret is a 409 on approval, never taken over.
- A route's `blocked` widens nothing when it is removed only if the person removing it means to: a migration or a default never unblocks a route.
- A label a box supplied is never shown in place of the routes it grants. A request's policy name, description and arguments are the asking box's words (ADR 26-11-02-022 §3): `SecretRequestPolicy` keeps them beside the routes the server resolved, and anything that renders a request — the console, the CLI, an API consumer — shows what each role grants (hosts, methods, paths, operations) beside its label. A box can describe write access as "read".
- An approval that replaces bindings never deletes a combined binding's delegation: a binding that both uses and delegates loses one side, and its children stay. Check every binding a replacement would update, split or delete — not only the one it keeps — against the raw and parent refusals (`checkReplaced`) before writing any, since one approval of a use part can otherwise delete a person's binding or a delegation every worker holds under.
- A limit on a box's request bounds what it resolves to, not only what it
  sent: a count of routes or documents does not bound their size, and a small
  document can expand an argument into a megabyte of paths, stored on the
  request and downloaded by every approver's inbox. `requestedPart` spends
  `agentcreds.MaxRequestRouteBytes` as each document resolves; a new way for a
  request to grow (another stored copy, another expansion) is spent from it too.
- Every approval path runs the raw refusal against the binding that delivers the variable, not only against the bindings it replaces. An addition replaces nothing, so `checkReplaced` never sees the raw binding it would stack on, and a raw row's sentinel is what the pool watches the value itself by: an addition there widens where the value may go on a sentinel ask (ADR 26-11-03-329 Deferred). `addBinding` answers 409 over a raw binding, and `store.sentinelGrants` stacks nothing on a raw row however an addition came to stand beside it.

- Refresh the grant clock after the final locked authority reads. A delegation
  may expire while waiting for a row lock; the pre-lock timestamp must not
  authorize a grant or calculate its receipt. Receipts are mutation results:
  remove them from sandbox request GET/list, preserving person history.
