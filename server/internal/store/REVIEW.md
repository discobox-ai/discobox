# Store Review Notes

- A read that decides what the caller writes next is made on the store a `Store.Transaction` callback was handed, never on the root store. With `databaseReadDsn` set, the root store reads from a replica that may not have the write a moment ago, and a decision made from it is silently wrong rather than failed — applying the configuration file's gateways after the default project moved once resolved `default` to the project it had just left. Inside a transaction every read is the transaction's.
- A new writer of a column a sandbox event reports (`desired_state`, `state`, `runtime_state`, `agent_status`) notes the sandbox on its transaction (`sandboxChanged`, `inSandboxTx`), and the event counter's row is the last lock any transaction takes: `sandboxEventBatch.record` takes it after locking every sandbox it projects, and `PruneSandboxEvents` writes the watermark on it after its delete. A writer that skips the note leaves the change out of the stream for good, since nothing re-reads it; a lock taken after the counter can deadlock two servers on one Postgres, which the first cut of the backfill could have done against a heartbeat (ADR 26-10-29-316 §§2–3).
- A sandbox event never reports an observation past the point its observer stopped reporting it: the pool stops reporting a sandbox at its archive (`ApplySandboxStateReports` skips it), so its runtime state and program are not projected from the archive on, and the complete sync that omits it puts its runtime state down. The first cut keyed only on the `archived` state, and an unarchive brought the pre-archive `running` and program back as new events (ADR 26-10-29-316).
- A batch that decides from a row what it writes over it reads that row locked. `ApplySandboxStateReports` read a pool's sandboxes without a lock and judged from them both whether a report was newer than the recorded one (`acceptSandboxStateReport`) and what the previous state was: on Postgres two batches in flight together both read the row as it was before either, and against a real database an older report overwrote a newer one in 194 of 300 races (ADR 0017 §10), a box that came back up was never handed back for its sentinels and proxy policy, and the latest event was left disagreeing with the row. `listSandboxesForPool` now locks the rows, in ID order, before the event counter. A writer also notes every sandbox row it writes (`sandboxChanged`) rather than a subset it judged changed: the event record compares the locked row with the sandbox's latest event, so a write that changes nothing still records nothing (ADR 26-10-29-316 §2).
- The event log and its position are read on the write handle (`eventLogRead`), never a read replica. A stream pages the log and then moves its cursor to the head it read; replicas lagging by different amounts let a page and that head disagree and skip events, and let a resume read its own cursor as past the head and be reset.
- Every transaction that locks more than one sandbox row locks them in sandbox ID order. A state report locks its pool's sandboxes in ID order (`listSandboxesForPool`); `ApplySandboxProgressReports` updated rows in the order the agent listed them, so a progress batch naming B then A and a state batch on the same pool could each hold one row and wait for the other, and Postgres fails one with a deadlock (40P01). It now writes in ID order. The event counter stays the last lock of all.
