## Claude Code channels: doc-sourced summary

**What it is.** A channel is an MCP server that pushes events into a running Claude Code session, so Claude can react to things that happen while you are away from the terminal. Channels can be one-way (alerts, webhooks) or two-way (chat bridges that expose a reply tool). Events only arrive while the session is open. For always-on use, run Claude in a background process or persistent terminal. ([channels](https://code.claude.com/docs/en/channels.md), [channels-reference](https://code.claude.com/docs/en/channels-reference.md))

**Status and gating**
- **Research preview.** Availability is rolling out gradually, and the flag syntax and protocol may change. Neither `--channels` nor `--dangerously-load-development-channels` appears in `claude --help` during the preview. ([channels](https://code.claude.com/docs/en/channels.md#research-preview))
- **Auth.** Requires claude.ai or Console API-key auth. Not available on Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry. ([channels](https://code.claude.com/docs/en/channels.md))
- **Team and Enterprise.** Blocked until an Owner enables channels at Organization settings &gt; Claude Code &gt; Channels (https://claude.ai/admin-settings/claude-code), or sets `channelsEnabled: true` in managed settings. Console orgs that deploy managed settings also need `channelsEnabled`. Pro and Max users without an org opt in per session with `--channels`. ([channels](https://code.claude.com/docs/en/channels.md#enterprise-controls))
- **Managed settings.**
  - `channelsEnabled`: master switch. Blocks everything, including the dev flag, when off.
  - `allowedChannelPlugins`: replaces the Anthropic default allowlist. Entries are `{ "marketplace": "...", "plugin": "..." }`. An empty array blocks all allowlisted plugins, but the dev flag can still bypass that.
- **Minimum version.** Not stated in the pages I fetched. A search summary claimed v2.1.80, but that comes from third-party write-ups, so I could not confirm it. The permission relay requires v2.1.234 or later (see below).

**CLI syntax**
- Shipped plugins use the `plugin:&lt;name&gt;@&lt;marketplace&gt;` form:
  ```bash
  claude --channels plugin:telegram@claude-plugins-official
  claude --channels plugin:fakechat@claude-plugins-official
  ```
  Several plugins can be passed space-separated.
- Custom/local servers use the dev flag, in either `plugin:` or `server:` form:
  ```bash
  claude --dangerously-load-development-channels server:webhook
  claude --dangerously-load-development-channels plugin:yourplugin@yourmarketplace
  ```
- The docs document `server:&lt;name&gt;` only for the dev flag. Plain `--channels server:...` is not documented, and `--channels` accepts only allowlisted plugins. Being in `.mcp.json` is not enough; the server must be named in one of these flags.
- The dev flag shows a full-screen warning that you must accept. It is per-entry: combining it with `--channels` does not extend the bypass to the `--channels` entries. It skips only the allowlist, not `channelsEnabled`. "Don't use it to run channels from untrusted sources." ([channels-reference](https://code.claude.com/docs/en/channels-reference.md#test-during-the-research-preview))
- The first session in a project also prompts for consent to use the new `.mcp.json` server.

**MCP server contract**
- Declare the capability: `capabilities: { experimental: { 'claude/channel': {} } }`. Add `tools: {}` for a two-way channel.
- Push an event with `notifications/claude/channel`, params `content` (string) and `meta` (string record):
  ```ts
  await mcp.notification({
    method: 'notifications/claude/channel',
    params: {
      content: 'build failed on main: https://ci.example.com/run/1234',
      meta: { severity: 'high', run_id: '1234' },
    },
  })
  ```
- `meta` keys must be identifiers (letters, digits, underscores). Keys with hyphens are silently dropped.
- The model sees:
  ```text
  &lt;\channel source="your-channel" severity="high" run_id="1234"&gt;
  build failed on main: https://ci.example.com/run/1234
  &lt;/channel&gt;
  ```
  `source` is set from the server name. For plugins the Quickstart shows `&lt;\channel source="plugin:fakechat:fakechat"&gt;`.
- `instructions` is a server-constructor field. Claude Code delivers it to Claude as context when the server connects. Use it to explain the tag attributes and whether and how to reply.
- Claude Code does not acknowledge notifications. `await mcp.notification()` resolves when the message is written to the transport. If the channel isn't registered or policy blocks it, events are dropped silently.
- Events queue and are processed in order. Notifications that arrive while Claude is busy are delivered together on the next turn.

**Two-way and permission relay**
- Reply tool: add `tools: {}`, then register `ListToolsRequestSchema` and `CallToolRequestSchema` handlers for a tool such as `reply(chat_id, text)`. The `instructions` string tells Claude to pass `chat_id` from the tag.
- Permission relay: declare `'claude/channel/permission': {}` under `experimental`. Only do this if the channel authenticates senders, because anyone who can reply can approve or deny tool use.
  - Claude Code sends `notifications/claude/channel/permission_request` with `request_id` (five letters, no `l`), `tool_name`, `description`, and `input_preview`.
  - Your server replies with `notifications/claude/channel/permission` carrying `request_id` and `behavior: 'allow' | 'deny'`.
  - Relay requires Claude Code v2.1.234 or later. The local terminal dialog stays open, and whichever answer arrives first wins.
  - Relay covers tool-use approvals only, not project-trust or MCP-consent dialogs.

**Minimal example (from the docs)**
The docs' webhook receiver is a single Bun file. Its core:
```ts
const mcp = new Server(
  { name: 'webhook', version: '0.0.1' },
  {
    capabilities: { experimental: { 'claude/channel': {} } },
    instructions: 'Events from the webhook channel arrive as &lt;\channel source="webhook" ...&gt;. They are one-way: read them and act, no reply expected.',
  },
)
await mcp.connect(new StdioServerTransport())
Bun.serve({
  port: 8788,
  hostname: '127.0.0.1',
  async fetch(req) {
    const body = await req.text()
    await mcp.notification({
      method: 'notifications/claude/channel',
      params: {
        content: body,
        meta: { path: new URL(req.url).pathname, method: req.method },
      },
    })
    return new Response('ok')
  },
})
```
Register it in `.mcp.json` as `"webhook": { "command": "bun", "args": ["./webhook.ts"] }`, start with `claude --dangerously-load-development-channels server:webhook`, and test with `curl -X POST localhost:8788 -d "build failed on main: ..."`. The docs also give a full two-way version with SSE output and permission relay.

**Security model**
- Each approved plugin keeps a sender allowlist, and non-allowlisted senders are silently dropped. Telegram and Discord bootstrap it by pairing (`/telegram:access pair &lt;code&gt;`, then `/telegram:access policy allowlist`). iMessage lets self-texts through and adds other handles with `/imessage:access allow`.
- Gate on the sender's ID (`message.from.id`), not the room's ID.
- Prompt-injection warning: "An ungated channel is a prompt injection vector."
- Channel messages are not shown as the reply text in the terminal. You see the inbound line and a "sent" confirmation.

**Headless and `-p`**
- The dev flag is ignored in `-p` mode and through the Agent SDK. The channel does not register.
- With `-p`, tools that need terminal input (multiple-choice questions, plan-mode approval) are disabled so the session does not stall.
- The docs do not say explicitly whether `--channels` works under `-p`. I could not confirm that.

**Gaps I could not confirm**
- Minimum Claude Code version for channels overall.
- Behavior of `--channels server:...` (undocumented).
- Whether channels work in `-p` mode.
- Exact persistence of events sent while no session is open. The docs say only that events arrive while the session is open and that unregistered events are dropped.
