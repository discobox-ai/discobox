## Context

A box is made two ways today, and a pool a third:

- **A Docker sandbox** runs the sandbox base image. Its pool places the agent
  layer (the platform bundle's last layer), the agent's units, `pins.json`
  and `sandbox.json` before the container starts. The agent fetches its
  pins' bundles through the pool's proxy and applies their features with its
  runner (`sandbox-agent/provision`). A snapshot of the plan makes the next
  create fast.
- **A Docker pool** is a container of the pool-agent image: the sandbox base
  image with `discobox-pool-agent`, BuildKit, a registry, the mediator,
  `discobox-pool-runc` and their units baked in at build time. Nothing is
  placed in it, and a pool-agent change is a new image and a new container.
- **A machine pool** (551) is a driver base given the pool-agent bundle, the
  bootstrap and a key, then the bundle's own `install`, a second installer
  beside the runner that knows two units and one package.
- **A machine sandbox** (551 §3) was to be given the agent layer and
  `sandbox.json`, then `discobox-sandbox-agent install`, which 0404de82
  removed with the runnable images it was also built for.

Bundles are named by kind everywhere they travel: the release manifest's
`Bundles.Platform`, `Harnesses` and `PoolAgent`; a sandbox's `Bundle` and
`PlatformBundle` columns; the pool API's `BundlePin.kind`; `agentlayer.Pins`'
`Platform` and `Harness`. How features are grouped into bundles is a
packaging choice, but each grouping is a schema.

The bundle client — read a pin's manifest, fetch the layers the store lacks,
check each against its digest, compose the tree — exists twice:
`sandbox-agent/bundlestore` behind `assets.discobox.internal`, and the
pull-through half of `pool-agent/assetcache` behind the server's asset
routes.

A box's identity is established two ways, each with half of what both want:

- **A pool** generates its own Ed25519 key and presents its public half at
  `POST /api/pools/register` with a single-use, 30-minute bootstrap token its
  provider minted (0063). Its private key never leaves it, but enrollment
  needs a public route that authenticates by a body field, a token table and
  its sweep, and a fallback that registers again when the server no longer
  knows the key. And a pool that provisions before its agent starts has no
  identity to fetch its bundles with.
- **A sandbox** is given its identity by its pool: the pool generates the
  sandbox's client keypair, signs its certificate with the pool's CA, and
  delivers the private key in the runtime-config document (`proxyagent`).
  Nothing enrolls, but the private key travels.

Every maker already has a channel into the box it makes that it trusts — the
one it places the bootstrap through, and which 423 §9 asks of every provider:
a container's exec, a machine's guest exec.

## Decision

### 1. A box is pinned to an ordered list of bundles

A **feature** is the unit of provisioning, as it is now. A **bundle** is a
group of features, built and published as one OCI artifact, and nothing
more: which features share a bundle is how they are released, not what
they are.

A box — a sandbox or a pool — is pinned to an **ordered list of bundles**,
each by name and digest, and applies them in that order: a later bundle's
features run after an earlier one's, and its manifest layer (env, volumes,
groups, seed files) composes over the earlier ones', as a harness bundle's
composes over the platform's now (`harness.ComposeBundleLabels`). Nothing in
the API, the pool's record or the box names a bundle's kind.

Three lists exist today, by what they are for:

| Box | List |
|---|---|
| A sandbox | the sandbox bundle (today's platform features), then its harness config's bundle |
| A pool | the pool bundle |
| A snapshot build | its sandbox's list, as now |

The server composes a sandbox's list from what its release names and what
its harness config names, and pins it at create, by an upgrade or a repair,
and for a stopped sandbox when what it was taken from moves, as 423 §7 pins
the two now. The release manifest names its bundles by role for the server
to compose from; a pool, a box and the API carry only the list.

**A moved pin restarts, never rebuilds.** No bundle digest is in a
sandbox's spec fingerprint. What its container is built with is the composed
manifest, whose digest (`HarnessManifestDigest` today) stays in it, so a
manifest-layer edit rebuilds as it does now, and any other move restarts the
box into its new list (423 §7's rule for the platform, now for every pin).

The server's sandbox columns become one list, migrated from the two pins
each existing row has, in order: platform, then harness.

*Amended 2026-10-24, before anything shipped against it:* the spec
fingerprint hashes the whole manifest, so dropping the two pin columns, or
taking the harness pin out of the delivered fingerprint, changes the
fingerprint of every delivered sandbox, and its pool replaces each container
at the next ensure — running ones included, which an observation alone
reaches. So a sandbox pinned before this ADR keeps its `platformBundle` and
`bundle` columns, is re-pinned in them, and keeps its harness pin in its
delivered fingerprint, as it was: it is never migrated, and nothing about the
list rebuilds it. A sandbox pinned since — created, imported, or one from
before bundles when it is first pinned to them — is pinned as the list alone,
and for it no bundle digest is in the fingerprint. The server reads and writes
pins through accessors that serve either form, and its composition order,
platform first, is what tells the list's pins apart; nothing past the server
does. The agent pin is new for every sandbox, and in neither fingerprint, so
a sandbox pinned before is pinned to the release's agent in place.

*Amended 2026-10-24, before anything shipped against it:* a sandbox pinned to
the release's agent in place is pinned to the release's platform with it, in
the form it was pinned in. An agent provisions the platform it ships with:
an older platform's features carry no `async` mark (whether a feature blocks
a box's readiness is now its own), so the new agent applying one would hold
every start of the box on all of them, and refuse any the repository turns
off. The person-facing upgrade view keeps naming what moved by role — the
platform, the harness, and now the agent — since it reads a sandbox against
its release rather than carrying a list to a pool; nothing past the server
does.

### 2. The agent is a bundle of its own, placed by whoever makes the box

The **agent bundle** is `discobox-sandbox-agent` alone: one layer, one file,
`FROM scratch`, multi-architecture. It replaces the agent layer's
last-layer convention (`agentlayer.AgentLayer`). It is not in a box's list:
it is what applies the list. The release names it, and a box records the
digest it was placed from beside its list.

Making a box is one contract, whoever makes it:

1. **Boot a base**: the Docker driver's sandbox base image as a container, or
   a driver's base as a machine.
2. **Place the agent** from the agent bundle.
3. **Enroll the box** (§4): it makes its key, and its maker records the
   public half.
4. **Place** the box's list as its pins, and its bootstrap — `sandbox.json`
   for a sandbox, `poolagent.Bootstrap` for a pool, each with what that box
   needs and nothing else, and no credential.
5. **Run one command**: `discobox-provision apply`, the agent's provisioning
   personality.

Placing and running are the provisioner of 551 §3, over `machine.Guest`,
for a container as for a machine: a Docker container's copy and exec are a
`Guest` too.

What `apply` does follows from the bootstrap:

- **A pool's**: fetch the list's bundles, apply every feature, and exit. The
  agent never runs as an agent there. The pool bundle's features lay and
  start the pool agent, its proxy and, on a Docker pool, BuildKit, the
  registry, the mediator and `discobox-pool-runc`. The pool agent starts on
  the key enrollment made, and registers nothing.
- **A sandbox's**: enable and start the agent's units, as `install` did. The
  agent then fetches and applies its list after its first runtime-config
  document, through its pool's proxy (0126 §6), as it does now.

The command is idempotent, and is run again whenever a box's list moves
while the box runs.

### 3. The bundle client is one library

The client half — given a list and a fetch, read each manifest, fetch only
the blobs the store lacks, verify every one against its digest, compose each
bundle's tree, and keep the trees its current and previous lists name — is
one package in the root module, used by:

- the agent, behind `assets.discobox.internal`, as now;
- `discobox-provision apply` on a pool, behind the server's asset routes;
- the pool agent's cache, behind the same routes, for what it fetches
  before serving it on.

`assetcache` keeps what only a pool has: its record of each sandbox's pins,
the handler scoped to them, and the sweep.

*Amended 2026-10-24, before anything shipped against it:* only the signed
fetch from the server's asset routes moves to the root module
(`pkg/poolassets`), which `discobox-provision apply` and the pool agent share.
The client half stays where it is: `bundlestore` in the agent's module,
`assetcache`'s fetch in the pool agent's. Moving it is a refactor of two
working clients whose stores differ (a box's trees, a pool's blobs), and
nothing this ADR decides needs it; it is deferred.

### 4. A box's maker enrolls it over the channel it made it with

One identity model for every box:

1. **Its maker asks the box for its public key** with one exec over the
   channel it made the box with: `discobox-provision identity`, which loads
   the box's key from its durable storage, makes it there first when it has
   none, and prints the public half. It is the only thing that makes a key,
   so a key is made on demand, the first time a maker asks, and never in a
   base or a snapshot. The private key never leaves the box, and asking
   again answers the same key.
2. **The box keeps it** where its agent reads it: `layout.PoolIdentityKey`
   for a pool (0063 §2).
3. **Its maker records it.** A provider records a pool's on the pool row:
   that is the pool's registration, made by the server itself. A pool signs
   a sandbox's certificate for it with its CA.
4. **The box authenticates to its maker's side as itself**: a pool with the
   assertions it signs with its key, as now; a sandbox with its certificate
   over mTLS, as now.

The trust is in the channel, not in a secret handed across it: the server
believes the key its provider read from the box it made, through the
channel it already trusts to place that box's bootstrap.

For a pool this means:

- **No bootstrap token.** `/api/pools/register`, its body-field
  authenticator, the token table and its sweep, and the agent's fallback to
  registering again go. The bootstrap carries no credential.
- **A pool is enrolled before it provisions,** so `apply` fetches its list
  from the asset routes as the pool, signing with the key the pool agent
  will run on, and no other credential exists for it.
- **A repair re-enrolls.** A provider reads the key again whenever it
  creates or repairs a pool, so a server that lost its record of a pool's
  key, or a box that lost its key with its volume, is mended by the
  provider rather than by a pool asking to be registered.

The model holds for a sandbox as written, and its pool already is its maker
and its CA. What changes for one — its key made in the box, and the
runtime-config document carrying its certificate and no private key — is
deferred (below).

### 5. A pool is provisioned once, and keeps what it provisioned

A pool box is made rarely, and boots fast afterwards from its own disk or
volume, so it takes the slow path every time it is made: no snapshot. On
every reconcile the provider compares its own record of what it placed — the
agent's digest and the list — with what the release now names. A moved
pool bundle is placed again and `apply` run again in the running box, which
restarts the units it moved. A moved agent alone runs nothing: the
provisioner is not what the pool runs. A moved base image makes a new box
(Docker) or none (a machine keeps its base), as a moved sandbox base image
does now.

The pool-agent image is retired. A Docker pool's container runs the sandbox
base image, its state on the volume it has now.

### 6. In development, a pool follows its bundle in place

The watcher builds the agent, sandbox, harness and pool bundles as OCI
layouts, as it builds the platform and pool-agent bundles now, and the
server serves them from its blob store. The sandbox base image is synchronized
to a pool's daemon as now. A pool-agent change moves the pool bundle's
digest, and the next reconcile re-applies it in the running container: no
image is built and no container is recreated. Build-mode hosts (macOS,
Windows) build the bundles on the pool's daemon before the pool is
reconciled, as `EnsurePool` converges the development manifest first now.

## Alternatives rejected

- **Keep the pool-agent image for Docker pools, and the bundle only for
  machines.** Two ways to make a pool, whose contents drift apart, as the
  image twins 423 retired did; and a pool-agent change in development stays
  an image build and a new container.
- **The pool-agent bundle's own `install` (551 §2).** A second installer
  beside the runner, which every new thing a pool runs — BuildKit, the
  registry, a feature a driver needs — becomes code in. 551 rejected the
  runner because the pool would carry the sandbox agent's runner; it now
  carries it on purpose, as its provisioner and nothing else.
- **Run the sandbox agent on the pool.** It would have to stand down every
  sandbox duty it has; only its runner is wanted.
- **The provider places whole trees, and nothing is fetched.** Every
  placement copies every bundle, streamed through a machine's copy on a VM,
  and the store's dedupe by layer is lost.
- **A provisioning token beside the bootstrap token.** A third credential
  with no role of its own, minted only to cover the moment before the pool
  registers, which enrollment by the maker removes.
- **The bootstrap token accepted for reads until it is redeemed.** It keeps
  the token, its route and its sweep, and gives one secret two jobs.
- **The maker generates the pool's key and places it**, as a pool does a
  sandbox's now. Enrollment needs no exec, but the private key travels; the
  box can make it and the maker read the public half for one exec.
- **The server as a CA for pools**, issuing certificates as a pool does for
  its sandboxes. The same protocol both ways, but what makes the model one
  is the key's lifecycle — made in the box, enrolled and renewed by the
  maker — not the wire format; pools keep their assertions.
- **Keep named kinds (platform, harness, pool-agent).** Every regrouping of
  features is a schema, API and migration change, and a pool's bundles and
  a sandbox's differ only in content.
- **Keep the agent as the sandbox bundle's last layer.** A pool would pin
  the sandbox bundle to get its provisioner, and placing the agent would
  depend on a layer-order convention inside a bundle whose grouping is now
  meant to change freely.

## Deferred

- **A snapshot of a provisioned pool.** One is made per pool, rarely, and it
  boots fast once made; revisit if pool creation time matters.
- **Regrouping the sandbox bundle's features** (core apart from the
  optional ones, or a pool and a sandbox sharing a bundle). The list makes
  it a packaging change; revisit when a box wants a subset.
- **A sandbox enrolled by its pool (§4).** The model is decided; the work —
  the sandbox making its client key, the pool reading the public half and
  signing it, and the runtime-config document dropping the private key — is
  not done with the pool's. Until it is, a pool generates a sandbox's
  keypair and delivers it, as now. Revisit once pools are enrolled.
- **A box with no maker**, such as a pool agent someone runs by hand on a
  host no provider made, has no channel to be enrolled over. None exists
  today, since only providers mint bootstrap tokens; revisit if one is
  wanted.

- **One bundle client in the root module (§3 as first written).** Revisit
  when a third client is wanted, or either store's fetch-and-verify changes:
  then they are moved together rather than changed twice.
- **A pool that turns its features off.** A pool whose sandboxes are
  machines runs none of `pool-builder`, but no such pool runs an agent yet
  (#127, #124), and `apply` takes no list of features to turn off. Revisit
  with the first one.

## Consequences

- The API's `BundlePin` loses `kind`; a create's `bundles` is ordered. The
  release manifest names the agent, sandbox, harness and pool bundles by
  role, the pool bundle in place of `PoolAgent`.
- `agentlayer.Pins` becomes a list, and `pins.json` with it.
- The server's sandbox pin columns become one ordered list (a migration).
- `discobox-provision` gains `apply`; the runner applies a list, and a pool
  bootstrap.
- The bundle client moves to the root module; `bundlestore` and
  `assetcache`'s fetch use it.
- `discobox-provision` gains `identity`. Signing a pool's assertion
  (`poolauth`) moves to the root module, since the provisioner signs as the
  pool before the pool agent runs.
- Pool bootstrap tokens go: `MintBootstrap`, `/api/pools/register` and its
  authenticator, the token table (a migration drops it), its sweep, and the
  agent's `ForceRegister`. Providers record a pool's key at create and
  repair. The pool agent refuses to start with no key, rather than making
  one.
- `dockerworker` makes a pool the way a pool makes a sandbox: boots the base,
  places, runs `apply`, records what it placed. The pool-agent image, its
  build and its release go.
- A step's record is keyed by its feature's directory too, and every
  feature's directory moves (`/opt/discobox/bundles/by-name/<bundle>`), so
  the first start of every existing box on the new agent runs every step
  again, once, and a snapshot built before is no help to it. Steps are
  idempotent; the cost is that one slow start per box.
- The VM provider (#127) and the pool's machine runtime (#124) use the same
  contract and provisioner, so a machine pool and a machine sandbox are the
  Docker ones on another `machine.Guest`.
