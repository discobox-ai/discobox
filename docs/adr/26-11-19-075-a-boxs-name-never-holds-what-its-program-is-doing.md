# 26-11-19-075 — A box's name never holds what its program is doing, and its handle is called a handle

- **Status**: Proposed
- **Date**: 2026-11-19

## Context

A box has five things a person could call its name:

| | What | Where | Set by | Unique |
| --- | --- | --- | --- | --- |
| handle | what commands and ssh resolve | `config.name`, the `sandboxes.name` column, an event's `name` | generated by the CLI at create (207) | in the project |
| given name | what a person or the agent called it | `~/.discobox/meta.json`, cached as `meta.name` / `meta_name` | `rename`, the agent, `config.metaName` at create | no |
| window title | what the harness says the session is about | the primary session's `title` (OSC 0/2) | the harness | no |
| msg | what the program is doing now | the primary session's `programStatus.msg` (OSC 7501) | the program | no |
| `displayName` | what a listing shows | computed, `services.SandboxDisplayName` | — | no |

`displayName` is the first of the given name, the window title, the handle
and the ID, followed by `: msg` while the box runs (618 §1). Three problems
follow.

**The name holds a status.** #1462: a Claude Code box lists as `Fix the
parser: keep all entries: 1 shell still running`. Everything outside the
server reads `displayName` as the box's name: a person reading `discobox ls`,
a script reading `-o json`, and the console, which stores it in a field
called `Name`. A status in the name is a bug to every one of them. 618 kept
it for the column it gave to what a box is doing. It came with workarounds
in every client:

- the CLI resolves an argument against `displayName` and against its
  column-truncated form, and against the given name, because the listed
  name stops resolving at the next report (618, Consequences; `sandboxListedAs`);
- the console's rename dialog must not prefill `displayName`, or the msg is
  written into the box's name for good (root `REVIEW.md`);
- the console works out the title without the msg itself, from the given
  name, the window title and the handle (`boxTitle`, `recordTitle`), which
  repeats the server's rule that `displayName` exists to keep in one place.

**`name` means opposite things.** `config.name` is the unique, generated
handle. `meta.name` is free display text. A create carries both, as
`config.name` and `config.metaName`. Each schema description spends a
sentence saying the other one is not it.

**Nothing on the wire is the name without the msg.** A client wanting it
has to rebuild it from `meta.name`, `config.name` and the agent status,
following the same rule the server does.

## Decision

### 1. The handle is `handle`

`config.name` becomes `config.handle`. The `sandboxes.name` column becomes
`handle` by a migration that renames it and its unique index. An event's
`name` becomes `handle`. The CLI's and the console's fields follow
(`ConfigName`, `BoxSettings.Name` → `Handle`). What a handle is does not
change. It is generated at create, unique in the project, the ssh `Host`
alias, and editable with `discobox admin box update`.

`config.name` is retired, not reused. No field ever takes `name` back with
another meaning on the create body, so a body written for either meaning
is never read as the other (§5).

### 2. `name` is what the box is called, and nothing more

`Sandbox.name` replaces `displayName`. It is computed on the server, as
before, and never empty. It is the first set of:

1. the given name (`meta.name`);
2. the primary terminal's window title;
3. the handle;
4. the ID.

It never contains the msg. It changes only when one of those changes: a
rename, or the harness retitling the session. It does not change as the
program works.

`meta.name` keeps its name. It is the file's own key (`meta.json`'s `name`),
and it is what `name` is whenever someone has set it. So "the box's name"
and "the name someone gave it" agree, except while nobody has given one. The
create body keeps `config.metaName` for the given name it seeds (207).

### 3. What the program is doing is `activity`

`Sandbox.activity` is the msg the primary terminal's program last reported
over OSC 7501. It is present only while the box is running and the program
has one (618 §2). It is made displayable as before. It never stands in for
the name.

Each client decides how to show it next to the name, and shows it as a
separate thing:

- `discobox ls` gets an ACTIVITY column after the agent state, and the NAME
  column is `name` alone (#1462's expectation);
- the console may draw it after the name on a row, in a tab or in the window
  title, styled as distinct from the name (`sandboxmeta.Title` keeps joining
  the two for that).

What a box is doing keeps its column in `ls`, which is what 618 was for.

### 4. A name resolves; an activity does not

An argument naming a box matches its ID or short ID, its handle, its given
name, or its `name` (whole or as truncated in `ls`'s column), under the
existing ambiguity rules. Since `name` holds no msg, a name copied from
`ls` keeps resolving until the box is renamed or retitled. The rename
dialog prefills `name`. The console reads `name` instead of rebuilding it,
and keeps only the newer-than-the-poll override from the pane's own title
and stream (618 §1).

### 5. Old clients keep working through a deprecation window

The server keeps sending `displayName` (`name: activity`, as now) and
`config.name` (the handle) beside the new fields. It accepts `config.name`
on create and update as the handle when `config.handle` is absent, and
refuses a body that sets both to different values. CLIs generated before
this change require `displayName` in the schema and send `config.name`,
so these stay until the oldest CLI the server supports no longer does. The
event keeps `name` beside `handle` for the same window.

## Alternatives rejected

**Keep `displayName` as it is and fix only `ls`** (show the given name or
title there). Rejected: `displayName` is the field every client reads as the
name, and #1462 also reports `-o json`. A display rule applied in one client
leaves the others showing the status and keeps the workarounds in §4.

**Drop the msg from the listing altogether** (618's "Always the title, never
the msg"). Rejected for the reason 618 gives: a working box is the one whose
work a person wants to see. Giving it its own field and column keeps that
without putting it in the name.

**Call the computed field `title`.** Rejected: it would be a fourth thing
called a title, beside the window title, the OSC 7501 record's `title`, and
the `title` of 618's `title: msg`. A person asking what a box is called
asks for its name.

**Make `name` the given name only, with no fallback.** Rejected: most boxes
are never named, and their window title is what tells them apart (618,
Context). A field that is usually empty would send every client back to
rebuilding the fallback.

**Reuse `config.name` for the given name and drop `config.metaName`.**
Rejected: an older CLI sends the generated handle as `config.name`. Read
with the new meaning, that would silently name every box it creates after
its handle, and leave it with no handle. A retired field name is never
given a new meaning (§1).

**Drop the handle and resolve boxes by ID or given name.** Deferred: the
handle is the ssh `Host` alias and what scripts already key on, and a given
name is not unique. Revisit if `ssh-config` moves to IDs and nothing else
needs a unique human-typable key.

## Consequences

- `discobox ls` shows a box's name steady while its agent works, and the
  status beside it. The suffix #1462 reports leaves the NAME column. If the
  program writes the status into its window title itself rather than into
  the OSC 7501 msg, it stays there: the window title is the harness's text.
  Which one Claude Code does, and whether its msg clears after the shell
  exits, is being reproduced on #1462. Neither changes this decision.
- The console's `boxTitle`/`recordTitle`/`unnamedName` rebuild of the name
  goes away. The root `REVIEW.md` rule on naming changes gets shorter: the
  rename-dialog trap is gone.
- The API schema, generated clients, CLI JSON output (`rename`, `resources
  -o json`), the in-box `discobox` skill, and the design docs listed in the
  root `REVIEW.md` all change in the implementing change.
- The column rename is a migration on durable state. Existing rows keep
  their handles, and the unique index keeps its constraint under the new
  name.
- For one window the wire carries both `displayName` and `name`, and both
  `config.name` and `config.handle`. Clients built after this change read
  only the new ones.
