# Approval form design workbench

Run from the repository root, in the development shell:

```sh
go tool task prototype:approvals
```

This is an interactive **design sketch**, using the console's actual dialog,
form, theme, focus and picker renderers. It starts with credential use, the
first screen under discussion. No design has been accepted yet.

- F2 switches between the current initial credential picker and the proposed card.
- Arrows move and change choices; Enter opens a picker; Ctrl-S submits the sketch.
- F5 resets; q or Ctrl-C quits. Resize the terminal to try narrower layouts.
- Every action shows a sample-only receipt. There is no API connection.

The current screen uses the actual `askAboutCredential` builder, with its action
callback replaced. Its later wizard screens are not demonstrated. The proposed
screen uses the existing form component, so Approve/Deny is a decision picker
rather than the separate buttons in the original chat sketch. New credential
creation is a placeholder. All names, routes and durations are fixtures.

Export an ANSI frame for sharing, including colors and the focused row:

```sh
go tool task prototype:approvals -- --capture --width 100 --height 36 > /tmp/approval-proposed.ansi
go tool task prototype:approvals -- --capture --current --width 100 --height 36 > /tmp/approval-current.ansi
```

Open the ANSI files with `cat` in a terminal. For issue/PR evidence, attach a
terminal screenshot or recording and link this runnable source at its commit.
The preview needs the repository and Go toolchain; it is not a standalone snippet.
No GitHub attachment or publication is performed by this workbench.

The preview code is gated by `-tags prototype`; it is excluded from normal builds.

## Manager's combined request

```sh
go tool task prototype:approvals:manager
```

Starts on **CURRENT**, using the downloaded `discobox-ai/manager`
`roles/manager-request.json` and the exact policy documents it names. F2 compares
with the first proposed form populated with all the same routes. PgUp/PgDn
scrolls the request; arrows remain assigned to the decision controls.

This intentionally reproduces the long list before redesigning it: 8 use policy
references and 21 delegation references, resolving to 52 distinct use routes and
77 distinct delegation routes. The baseline also shows the role groups and
summaries generated by the product code. The proposed view currently flattens
the routes; it is an overflow reproduction, not an agreed solution.

Fixture source: GitHub Contents API, fetched 2026-11-05 from
`discobox-ai/manager/roles`. `manager/source.json` records each source blob SHA.
Policy resolution uses `credentialpolicy.ResolveDocument` and the same
normalization/deduplication rule as the server. No credential request is sent.
The box identity, age and available credentials are illustrative; the JSON
request and policy documents are copied verbatim. The preview omits the
transport-only `wait` field.

For other fixtures, pass `--request PATH --policy-root CHECKOUT` to
`prototype:approvals`; policy paths in the JSON are relative to CHECKOUT.

The proposed route lists now use aligned METHOD, PATH and OPTIONS columns.
Each list sorts by host/path first, method second, options as a final tie-breaker.
Multi-host/path routes expand to one row per host/path; method lists stay together.
`*` means any HTTP method. GraphQL, MCP and blocked markers appear in OPTIONS.
Column widths are shared between the use and delegation lists. Long rows still
wrap at the card edge on narrow terminals; this pass does not solve that layout.

### Protocol and host grouping

The latest proposed layout replaces the flat OPTIONS table with protocol groups
in HTTP, GraphQL, MCP order inside each Use/Delegate section. Each protocol groups
hosts alphabetically, showing the host once above its table. Rows sort by path,
then method. GraphQL tables show operation and fields; MCP tables show tools.
Unrestricted HTTP methods are omitted from GraphQL/MCP tables, while explicit
method restrictions remain visible. If a host group contains blocked routes,
its table includes ACCESS with ALLOW/DENY; deny rows use the alert color.

### Separate use and delegation decisions

The proposed combined request is now two screens: use (1 of 2), then delegation
(2 of 2), with only that part's routes and an independent Accept/Deny picker.
Ctrl-S confirms either decision and advances. Accepting use locks credential
and duration on delegation; denying use carries the selections forward but
leaves them editable. F5 or Esc resets the sample flow. The final receipt records
both decisions. No live request is submitted at either step.

Two sample credentials are available so the deny-use/edit-delegation path can be
tried. New credential creation remains a placeholder and cannot be accepted.

Protocol and host now share a heading line (for example `HTTP api.github.com`),
with the table header immediately below it. The same applies to GraphQL and MCP.

### Upcoming scope and lifetime choices

PR #650 permits additions without expiry; the preview now offers Forever.
The scope proposal in merged PR #638 defines Requested routes (default),
Requested hosts, and Anywhere. Each proposed screen now has an independent Scope
picker. Accepting use locks credential and duration on delegation, while scope
starts again at Requested routes and remains editable. Requested hosts drops
request-level method/path/protocol/blocked restrictions; credential and parent
restrictions remain. Anywhere adds no grant restriction. Picker hints describe
these effects. The displayed route tables remain the original requested access.
This models the design choices only; backend integration and live ceiling,
replacement and addition previews are still outside the sample program.

Changing Scope now updates the upper grant restriction list immediately:
Requested routes shows protocol/host tables, Requested hosts shows host-only
access for any method/path/protocol, and Anywhere shows no grant restriction.
Changing scope resets body scrolling. Credential and parent ceilings remain
separate and are called out below; the preview does not flatten them into the
selected binding restriction. This supersedes the earlier static requested-list
behavior.

### Modal decision buttons

Accept/Deny are now focusable buttons below the fields, replacing the Decision
picker and Ctrl-S. Tab/Down moves from Scope to Accept; Left/Right selects a
button; Enter activates it. Tab moves Accept -> Deny -> first editable field;
Up returns to Scope. Enter on a field still opens its picker. Locked fields on
the delegation screen are skipped. This supersedes the earlier Ctrl-S controls.
The shared dialog renderer supports these buttons only when explicitly supplied;
other forms retain their existing controls. Mouse input is not wired in this
standalone design workbench.
